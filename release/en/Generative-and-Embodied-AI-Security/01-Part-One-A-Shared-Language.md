# Part One: A Shared Language

## Guide to This Part

A generative AI system may start with a single question and answer. It may also reach all the way to databases, media publishing, software tools and physical actuators. Security discussions, faced with implementations this different, most easily start from the name of an attack or a model. One group asks first whether it is jailbreaking. Another asks first which kind of model it is. Part One takes a different starting point. It establishes, to begin with, which objects exist in the system, where trust changes, who consumes the outputs, and what the evidence actually observed. Draw these relationships clearly, and new technology names cannot deprive the analysis of its coordinates.

Chapter 1 builds the capability chain. It runs from external input, context, model output, candidate plans, authorization and execution through to feedback. The key change here is not a "smarter" model. It is that probabilistic outputs progressively acquire state, identity and real-world capability. Chapter 2 expands that chain into system objects and the U0—U6 trust interfaces. It distinguishes where an attack first crosses a boundary, what enables later propagation, and which control ultimately releases an action. Chapter 3 then answers how to measure. Sampling units, denominators, attack budgets, scoring rules and evidence layers jointly produce a percentage.

The three chapters deal with the system, the path and the evidence, in that order. Readers do not need to master every attack algorithm first. They need only ask three questions repeatedly. Does the sentence at hand describe a model output, a system plan, or an external consequence? Where is the interface at which an attack first obtains influence beyond its allowance? Up to which layer of conclusions do existing operations and records provide support? The same set of questions carries through the five subsequent parts. This part is therefore no abstract conceptual warm-up. It is the shared coordinate system by which the whole book judges whether terms, cases and numbers can be compared with one another.

On a first pass, the detailed symbols in the formulas can be ignored. Walk once along the object relationships on either side of the variables. The core of the attack success rate formula, for example, is not the fraction itself. It is whether the numerator's "success" corresponds to the sampling unit in the denominator. The risk chain product is no different. A small decimal is not the point; knowing which control actually changed which condition is. Only once the objects, the consumers and the consequence layers are clear do formulas compress relationships. Until then they remain a new barrier to reading.

The normal case in this part is a read-only question-answering service. Its outputs stop at the information layer. An error spreads only if a person or downstream software adopts it separately. The boundary case attaches the same model to payment or mechanical control. There, model outputs can be parsed into actions and acquire permissions. Model weights may be shared between the two. System risk is not. With this distinction in hand, a reader entering Part Two can see why one answer will not serve. Prompt injection, retrieval poisoning and tool overreach cannot be answered by the same single "model safety score".

This part also sets the evidence discipline for the whole book. Unknown versions, missing denominators, failed runs and unverifiable consumers must not be deleted in silence. Static files, local fixtures, simulated closed loops and field incidents each have value. A conclusion, however, reaches only as far as the layer actually reached in operation. That constraint lets later chapters deliver honest, useful engineering judgments even against new models and incomplete public materials.
